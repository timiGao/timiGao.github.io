终于建站了。

经过一番折腾，我终于拥有了一个完全由自己掌控的个人博客。这篇文章既是对建站过程的简单记录，也是一次 Markdown 排版的基准测试。

## 🛠 技术栈与工作流

为了追求极简和高度掌控力，我避开了臃肿的动态博客系统（如 WordPress），选择了符合现代开发标准的纯静态生成方案：

*   **核心引擎**：[Hugo](https://gohugo.io/)[^1] —— 一个用 Go 语言编写的极速静态网站生成器。只需一个命令即可瞬间生成全站 HTML。
*   **外观主题**：**PaperMod** —— 极其干净、阅读体验优秀且对移动端友好的极简主题。
*   **自动化部署**：**GitHub Actions** + **GitHub Pages**。这也是整套方案的核心：本地 Git 仓库只保留纯净的 Markdown 源码，推送到 GitHub 后，云端服务器会自动触发编译并完成发布。

## 🚧 踩坑与排错记录

今天的建站过程并非一帆风顺，遇到了两个极其典型的环境与配置陷阱：

1.  **WSL 本地预览网络隔离**：在 WSL (Ubuntu) 下运行 Hugo 本地服务器时，由于 NAT 模式的代理限制，Windows 宿主机无法直接访问 `localhost`。
2.  **GitHub Pages 部署双轨冲突**：在配置自动化工作流时，不慎将本地测试生成的 `public/` 编译产物推上了仓库。这导致 GitHub 默认的“分支部署”逻辑与我自定义的 Actions 脚本发生冲突，网站一度陷入死循环的 404 错误。在清理 Git 追踪缓存并强制指定 Source 为 GitHub Actions 后，问题才得以彻底解决。

## 💡 心得与展望

选择自己搭博客，最大的意义在于 **100% 的数据掌控权**。没有平台的算法推荐，没有内容审查机制，也没有强制插入的广告。它就像互联网上的一块自留地。

后续我计划将这里作为主要的输出阵地，记录学习心得、技术笔记以及一些生活思考。

这只是第一篇文章，但绝不是最后一篇。

[^1]: 这里有一个极其容易踩坑的细节：安装 Hugo 时必须获取 `Extended`（扩展）版本，因为现代主题通常依赖它来编译 SCSS/SASS 样式表，而很多 Linux 发行版自带的包管理器默认提供的都是陈旧的普通版。
